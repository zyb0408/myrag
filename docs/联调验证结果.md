## 二、验证方法

1. **接口契约逐项断言**：`server/tests/integration_test.py` 覆盖全部 17 个 REST 端点
   （正常路径 + 错误路径），逐项断言 HTTP 状态码、`code`、`message`、`data` 结构与字段含义；
2. **SSE 流式行为验证**：发起 `POST /api/chat/:convId`，断言
   `text/event-stream` 响应头、`data: {choices[0].delta.content}` 增量块、`data: [DONE]` 结尾，
   以及助手消息持久化（旧实现缺陷修复项）；
3. **前端解析契约比对**：对照 `client/src/services/api.ts`（`res.ok` + `body.message` / `resp.data`）
   与 `client/src/services/sse.ts`（`data:` 行 / `[DONE]` / `{"error":...}` / `choices[0].delta.content`）
   逐字段确认新响应格式与之完全匹配；
4. **端到端链路验证**：启动 Vite dev server，经 `http://localhost:5173/api/*` 代理访问
   BFF → Mock RAGFlow，模拟真实浏览器请求链路（health / login / chat-assistants 均通过）。

## 五、与原实现（TypeScript/Express）行为一致性结论

1. **接口契约 100% 一致**：全部 17 个端点（路径、方法、请求参数、响应 `code/data/message`
   结构与字段含义、错误码与错误文案）与旧实现逐字一致；
2. **SSE 转发格式一致**：`data: {choices[0].delta.content}` / `data: [DONE]` / `data: {"error":...}`
   与前端 `client/src/services/sse.ts` 解析逻辑完全匹配；
3. **存量数据兼容**：复用旧 `ragflow-chat.db`，bcrypt 校验旧 `$2a$` hash 成功、JWT 签发/校验正常、
   表结构与列名一致；
4. **前端零改动**：`client/` 目录未发生任何变更，经 Vite 代理端到端验证通过；
5. **唯一行为差异（缺陷修复）**：旧实现流式结束后保存助手消息存在参数缺失缺陷
   （`execute` 缺参导致助手消息永不落库，且前端额外收到错误事件）；新实现按原意图修复，
   助手消息正确持久化。该修复不涉及接口契约变更（详见 REFACTOR.md 第七节）。
