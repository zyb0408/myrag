## 修复发送消息被 401 拦截的权限 bug

- 现象：选知识库 → 新建对话 → 输入问题发送，被后端 require_auth 拦截返回 401。
- 根因：前端 `client/src/services/sse.ts` 的 `streamChat()` 用裸 fetch，headers 只有 `Content-Type`，漏带 `Authorization`；而 `api.ts` 的 `request()` 会自动从 localStorage 读 token 加 `Bearer`。所以普通接口正常、唯独发送消息 `POST /api/chat/:convId`（走 sse.ts）被拦。
- 修复：(1) `api.ts` 把 `getToken()` 改为 `export`；(2) `sse.ts` import getToken，发送前构造带 `Authorization: Bearer <token>` 的 headers。Vite HMR 自动生效，无需重启。
- 结论：后端 `require_auth`（`server/app/security.py`）逻辑本身正确（标准 JWT Bearer 校验：取 header → Bearer 前缀 → verify_token → AuthUser），无需改动；问题在前端漏带 token。
- BFF 权限分层梳理：公开层（auth/login、auth/reset-password、knowledge-bases、chat-assistants、health，无鉴权）/ 需登录 require_auth（conversations/*、chat/*、auth/me，按 user_id 隔离）/ 需管理员 require_admin（admin/*，= require_auth + isAdmin）。

## 问答全链路梳理 + 前端渲染分析

- 流程：前端 `ChatWindow.handleSend` → `sse.ts streamChat`(POST /api/chat/:convId，带 JWT) → BFF `chat.py`(require_auth+归属校验+存用户消息+取历史) → `ragflow.py chat_completion`(POST /api/v1/openai/{assistant_id}/chat/completions，带 RAGFLOW_API_KEY) → RAGFlow 检索+流式生成 → BFF `event_stream` 逐 chunk 转发+累积 full_content+流结束存 assistant(references=None)+发 [DONE] → 前端 `sse.ts` 解析 data: 累加 streamingContent → `MessageList` 流式渲染 `MessageBubble`(markdown-it+光标)。
- 渲染内容：✅ 助手回复文本(markdown-it 转 HTML, v-html) ✅ 流式光标(蓝色闪烁) ✅「思考中」占位(streamingContent 为空时) ✅ 用户消息(纯文本 pre-wrap)；自动滚动到底。
- 重要发现：**references（引用来源）全链路未处理**——`Message` 类型有 references 字段，但 BFF `chat.py` 存 assistant 消息时 references=None；`sse.ts` 的 SSEChunk 无 references 字段；`MessageBubble` 只接收 content 不渲染引用。RAGFlow 返回的引用来源被丢弃。如需展示来源需 BFF 解析 RAGFlow 的 reference 字段 + 前端渲染。
